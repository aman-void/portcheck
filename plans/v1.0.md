# Portcheck v1.0 Implementation Plan

## 1. Purpose

Portcheck v1.0 is the first **stable production release**.

The purpose of v1.0 is not to introduce a large collection of new functionality.

Instead, v1.0 should take the functionality developed across v0.1-v0.5 and make it:

- stable
- predictable
- documented
- portable
- testable
- distributable
- backward-compatible within the v1.0 contract
- suitable for real developer use

The project should transition from:

> “An AI-built experimental Go CLI”

to:

> “A small, reliable developer tool that happens to have been built through an AI-driven incremental engineering process.”

The core functionality should remain intentionally small.

---

# 2. Starting Point

v1.0 starts from an accepted v0.5 implementation.

Before beginning v1.0 work, verify:

```bash
gofmt -w .
go test ./...
go vet ./...
go build ./...
go list -m all
```

The agent must inspect the entire existing project before making changes.

Do not assume that previous versions were implemented exactly according to their plans.

The actual repository is the source of truth.

---

# 3. v1.0 Philosophy

The central rule for v1.0 is:

> **Stabilize before expanding.**

Do not use v1.0 as an excuse to add:

- UDP
- HTTP probing
- TLS inspection
- network scanning
- packet capture
- service management
- AI diagnostics
- cloud integrations
- configuration servers
- plugins
- databases

None of these are required for a stable Portcheck 1.0.

Human beings already have enough software that does seventeen unrelated things badly.

# 8. Public API Principles

The public API should expose concepts rather than CLI implementation details.

Good:

```go
result, err := portcheck.Check(ctx, "127.0.0.1", 8080)
```

Potentially good:

```go
result, err := portcheck.Connect(ctx, "localhost:8080")
```

Bad:

```go
portcheck.ParseCLIArguments(...)
```

Bad:

```go
portcheck.RenderHumanOutput(...)
```

Bad:

```go
portcheck.InternalLinuxSocketScanner(...)
```

The library should remain useful independently of the CLI.

---

# 9. Avoid API Overengineering

Do not expose every internal abstraction.

For example, do not expose:

```go
type CheckerFactory interface {}
type ProcessInspectorFactory interface {}
type ConnectivityProvider interface {}
type ResultRenderer interface {}
type PlatformResolver interface {}
```

unless there is an actual public use case.

A tiny tool does not need an enterprise architecture diagram to check port 8080.

# 10. Semantic Versioning

v1.0 establishes semantic-versioning expectations.

The project should follow:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
1.0.0
1.0.1
1.1.0
2.0.0
```

At v1.0:

### Patch

Bug fixes and non-breaking corrections.

```text
1.0.0 → 1.0.1
```

### Minor

Backward-compatible functionality.

```text
1.0.0 → 1.1.0
```

### Major

Breaking API or CLI changes.

```text
1.0.0 → 2.0.0
```

Document this policy.

Do not blindly assume this exact command is correct for every platform.

Release builds should be generated independently for the intended target platforms.

# 18. Process Inspection Platform Contract

Process inspection is the most platform-sensitive component.

For each supported OS, document:

- whether process inspection is supported
- what information is available
- permission requirements
- known limitations

For example:

```text

  PID: supported
  Name: supported
  Executable: supported where accessible

macOS
  PID: supported where implemented
  Name: supported where implemented
  Executable: may be permission restricted

Windows
  PID: supported where implemented
  Name: supported where implemented
  Executable: may require additional permissions
```

Do not pretend every OS exposes identical information.

# 26. Error Model

v1.0 should establish consistent error semantics.

Errors should answer:

1. What operation failed?
2. What input caused it?
3. Is it an expected result or a program failure?
4. Can the caller reasonably act on it?

Prefer wrapped errors:

```go
fmt.Errorf("connect to %s: %w", address, err)
```

rather than losing the original cause.

Use sentinel or typed errors only when callers genuinely need programmatic classification.

Do not create dozens of custom error types.

---

# 27. Exit Code Contract

Document final exit codes.

A reasonable contract is:

```text
0   success / requested condition satisfied
1   expected negative result
2   invalid command-line input
3   unexpected/system failure
```

The exact meanings must match the accumulated implementation.

Examples:

```text
port is in use
```

may produce:

```text
1
```

while:

```text
invalid port 99999
```

produces:

```text
2
```

and:

```text
unexpected internal failure
```

produces:

```text
3
```

Do not change these meanings casually after v1.0.

---

# 30. Watch Mode Stability

Review the v0.3 watch implementation carefully.

Verify:

- initial state is emitted
- subsequent output only occurs on meaningful state changes
- polling interval is respected
- Ctrl+C works
- ticker resources are released
- no busy loops exist
- errors do not cause infinite retries
- process changes are handled correctly
- output remains readable
- JSON mode remains machine-readable if supported

Watch mode should not leak goroutines or timers.

---

# 31. Wait Mode Stability

Review:

```bash
portcheck --wait 8080
```

and:

```bash
portcheck --wait-in-use 8080
```

Verify:

- cancellation works
- timeout works
- multiple ports behave correctly
- state is evaluated consistently
- unexpected errors terminate appropriately
- polling does not consume excessive CPU
- ticker resources are released

No infinite retry loops on unexpected errors.

---

# 32. `--find` Stability

Review:

```bash
portcheck --find 3000
```

Verify:

- search begins at requested port
- search does not wrap around
- upper bound is 65535
- host selection works
- occupied ports are skipped
- result is deterministic for a stable environment
- errors are not incorrectly treated as free ports

---

# 33. Range Handling

Review:

```text
3000-3010
```

Verify:

- inclusive bounds
- start <= end
- invalid syntax rejected
- duplicates removed according to established semantics
- input order preserved where promised
- maximum port is 65535

Do not introduce unnecessarily large integer abstractions.

# 72. Final Product Definition

Portcheck 1.0 should be able to answer these questions reliably:

```text
1. Is this TCP port available?

2. Which local process is using this TCP port?

3. Can I establish a TCP connection to this endpoint?

4. How long did that connection take?

5. What factual information can I gather about this local endpoint?

6. Can another program consume the results through JSON?

7. Can I use the functionality from Go code?

8. Can I install and run the tool on supported platforms?
```

It should deliberately **not** claim to answer:

```text
Is the application healthy?
Is the firewall broken?
Is the network route correct?
Is the HTTP service healthy?
Is TLS configured correctly?
Why exactly is the network failing?
```

Those are different problems.

The v1.0 experiment succeeds if a developer can:

then use:

```bash
portcheck 8080
```

- understandable
- scriptable

# 74. Post-v1.0 Boundary

After `v1.0.0`, new features should be evaluated against the stable product rather than automatically added.

Potential future releases may include:

```text
v1.1
  small backward-compatible improvements

v1.2
  additional platform support

v2.0
  only if genuinely breaking functionality is justified
```

Potential future features such as:

- UDP
- HTTP probing
- TLS diagnostics
- advanced networking
- richer service detection
- package distribution
- additional integrations

must be evaluated separately.

They should never be added merely because an AI agent suggested them.

# 75. The Portcheck Experiment

The complete development sequence is now:

```text
v0.1
Foundation
    ↓
v0.2
Ranges + JSON + Go API
    ↓
v0.3
Hosts + Watch + Wait
    ↓
v0.4
Process Inspection
    ↓
v0.5
Connectivity + Diagnostics
    ↓
```

The important part is not that an AI agent can write each version.

The important part is whether the agent can:

```text
understand existing code
        ↓
make constrained changes
        ↓
preserve previous behavior
        ↓
write meaningful tests
        ↓
detect regressions
        ↓
respect architectural boundaries
        ↓
review its own work
        ↓
prepare a stable release
```

That is the actual engineering experiment behind Portcheck.
