# Portcheck v0.2

> Expansion release: port ranges, available-port discovery, JSON output, and a small reusable Go API.

---

# 1. Version Objective

Version `0.2.0` builds directly on the accepted v0.1 implementation.

The goal is to make Portcheck useful for:

- checking ranges of ports
- finding available ports
- consuming results programmatically
- integrating with shell scripts and other tools
- using Portcheck's core functionality from Go code

The CLI behavior established in v0.1 must remain stable unless explicitly changed by this specification.

---

# 2. Starting Point

The implementation must begin from an accepted v0.1 codebase.

Before making changes, verify:

```bash
go test ./...
go vet ./...
go build ./cmd/portcheck
```

If v0.1 is not in a healthy state, fix the existing regression first.

Do not begin v0.2 feature work on top of a broken v0.1 implementation.

# 4. Design Goals

v0.2 should accomplish four major things:

```text
                v0.1
                  │
                  ▼
          ┌───────────────┐
          │ Port checking │
          └───────┬───────┘
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      Ranges    JSON      Go API
        │         │         │
        └─────────┼─────────┘
                  ▼
             v0.2.0
```

The important architectural change is that the underlying port-checking functionality becomes reusable independently of the CLI.

---

# 5. Technical Constraints

Continue all v0.1 constraints:

- Go standard library only
- zero third-party Go dependencies
- no CLI framework
- no unnecessary abstractions
- no unnecessary concurrency
- no shell commands for core functionality
- no OS-specific code unless explicitly required
- no AI functionality inside Portcheck

Use idiomatic Go.

Prefer simple APIs.

---

# 6. Port Range Syntax

Support:

```bash
portcheck 3000-3010
```

This represents:

```text
3000
3001
3002
...
3010
```

Both endpoints are inclusive.

---

# 7. Range Validation

Valid examples:

```text
3000-3005
1-10
65530-65535
```

Invalid examples:

```text
0-10
-1-10
10-0
65530-65536
abc-100
100-abc
3000-
-3000
3000--3010
3000-3010-3020
```

The range parser must reject malformed expressions.

Both endpoints must satisfy:

```text
1 <= port <= 65535
```

The start port must not be greater than the end port.

---

# 8. Single Ports and Ranges

v0.2 must support mixing single ports and ranges.

Example:

```bash
portcheck 3000 8080-8083 5432
```

Conceptually this expands to:

```text
3000
8080
8081
8082
8083
5432
```

The implementation must then deduplicate the resulting ports.

---

# 9. Deduplication

Duplicate ports must continue to be checked only once.

Example:

```bash
portcheck 3000 3001-3003 3002
```

The resulting unique sequence is:

```text
3000
3001
3002
3003
```

The first occurrence determines ordering.

Do not sort the ports automatically unless explicitly required.

---

# 10. Range Expansion Limits

Range expansion can theoretically create up to:

```text
65535
```

ports.

The implementation must avoid accidental unbounded memory usage.

Since the legal TCP port space is bounded to 1-65535, a full range is inherently finite.

However, do not create multiple redundant representations of the same expanded range.

A simple:

```go
[]int
```

is acceptable if it keeps the implementation clear.

Do not build an elaborate range abstraction unless required.

---

# 11. Range Output

Normal human output should remain compatible with v0.1.

Example:

```bash
portcheck 3000-3003
```

Output:

```text
PORT    STATUS
3000    FREE
3001    IN USE
3002    FREE
3003    FREE
```

Input order should be preserved.

---

# 12. Large Range Behavior

Checking a large range may require many socket operations.

For v0.2:

- correctness is more important than maximum speed
- sequential checking is acceptable
- do not introduce a worker pool by default
- do not introduce unbounded goroutines

Example:

```bash
portcheck 1-65535
```

must be handled safely, even if it is not optimized for maximum speed.

Performance optimization can be considered in a later version if measurements justify it.

---

# 13. `--find`

Introduce:

```bash
portcheck --find 3000
```

The command should search from the supplied port upward until it finds a free port.

Example:

```text
3000 IN USE
3001 IN USE
3002 FREE
```

The primary result should identify the available port.

A concise output could be:

```text
3002
```

The exact output contract must be consistent and documented.

---

# 14. `--find` Semantics

The starting port must be valid:

```text
1 <= start <= 65535
```

The search should continue:

```text
start
start + 1
start + 2
...
65535
```

If no free port exists:

- return an appropriate error
- use the established error/exit semantics
- do not silently wrap around to port `1`

Port ranges should not wrap around.

---

# 15. `--find` with Multiple Arguments

Do not support ambiguous syntax such as:

```bash
portcheck --find 3000 4000
```

unless the CLI semantics are explicitly defined.

v0.2 should keep `--find` simple.

Recommended:

```bash
portcheck --find <starting-port>
```

Exactly one starting port.

If additional positional arguments are supplied, return a clear CLI error.

---

# 16. JSON Output

Introduce:

```bash
portcheck --json 3000 8080
```

Expected conceptual structure:

```json
[
  {
    "port": 3000,
    "status": "free"
  },
  {
    "port": 8080,
    "status": "in_use"
  }
]
```

The JSON representation should be generated from structured results.

Do not create a second independent checking implementation just for JSON.

---

# 17. JSON Schema

The initial JSON result should contain stable, simple fields.

Recommended:

```json
{
  "port": 3000,
  "status": "free"
}
```

Possible statuses:

```text
free
in_use
error
```

If an error occurs, an error field may be included.

Example:

```json
{
  "port": 8080,
  "status": "error",
  "error": "permission denied"
}
```

Do not expose internal Go error types directly.

JSON should expose human-consumable strings and stable fields.

---

# 18. JSON Output Stability

Once introduced, JSON field names become part of the CLI contract.

Use stable names:

```text
port
status
error
```

Do not expose internal implementation names such as:

```text
statusCode
internalError
checkerResult
```

Avoid unnecessary nested structures.

Keep the schema simple.

---

# 19. Quiet Mode + JSON

Define behavior explicitly.

These modes should not be silently combined if their semantics conflict.

Recommended:

```bash
portcheck --quiet 8080
```

continues to mean:

```text
FREE
```

while:

```bash
portcheck --json 8080
```

means:

```json
[
  {
    "port": 8080,
    "status": "free"
  }
]
```

If both are supplied:

```bash
portcheck --quiet --json 8080
```

the CLI should reject the combination with a clear error.

Do not invent a strange hybrid format.

---

# 20. Human Output vs JSON

The same underlying result must drive both.

Conceptually:

```text
             TCP checker
                  │
                  ▼
           []Result
            /     \
           /       \
          ▼         ▼
      Human       JSON
      output      output
```

This is important.

The output format must not influence how the port is checked.

---

# 21. Reusable Go API

v0.2 introduces a small public Go API.

The API should expose the core functionality without exposing CLI concerns.

Potential usage:

```go
result, err := portcheck.Check(ctx, 8080)
```

For multiple ports:

```go
results, err := portcheck.CheckPorts(ctx, []int{
    3000,
    8080,
    5432,
})
```

The exact API may differ if a simpler design is demonstrably better.

---

# 22. Public API Principles

The public API must be intentionally small.

Expose only what external Go consumers actually need.

Potential public concepts:

```go
type Status string

const (
    StatusFree   Status = "free"
    StatusInUse  Status = "in_use"
    StatusError  Status = "error"
)

type Result struct {
    Port   int
    Status Status
    Err    error
}
```

However, do not expose `Err error` if that produces an awkward or unstable public API.

The agent should choose the smallest clean design.

---

# 23. Context Support

If the public API can perform operations that may block, prefer context-aware APIs.

For example:

```go
func Check(ctx context.Context, port int) (Result, error)
```

However, do not add `context.Context` to every internal function merely for consistency.

Use it where cancellation and deadlines matter.

---

# 24. Library and CLI Separation

The dependency direction should be:

```text
CLI
 │
 ▼
Public/core Portcheck API
 │
 ▼
TCP checker
```

Not:

```text
TCP checker
 │
 ▼
CLI
```

The core must not import the CLI package.

The CLI depends on the core.

---

# 25. Package Placement

The public API may be placed at the module root:

```text
portcheck/
├── portcheck.go
```

with internal implementation:

```text
internal/
├── checker/
└── cli/
```

Possible structure:

```text
portcheck/
├── cmd/
│   └── portcheck/
│       └── main.go
│
├── internal/
│   ├── checker/
│   └── cli/
│
├── portcheck.go
├── portcheck_test.go
├── go.mod
└── ...
```

Do not create a `pkg/` directory simply because many Go projects have one.

A public package at the module root is perfectly valid.

---

# 26. API Validation

The public API must validate input.

For example:

```go
portcheck.Check(ctx, 0)
```

must return a meaningful validation error.

Likewise:

```go
portcheck.Check(ctx, 65536)
```

must fail validation.

Do not assume library consumers have already validated input.

---

# 27. Library Error Design

Library errors should be distinguishable from CLI errors.

The CLI may render:

```text
error: invalid port "70000": must be between 1 and 65535
```

The library should provide a structured error that callers can inspect where useful.

For example, a sentinel or typed error may be appropriate.

Do not require consumers to parse human-readable error strings to determine whether input was invalid.

Keep the error API minimal.

# 32. `--find` Tests

Test:

```text

```

Use dynamically controlled test listeners.

Do not assume any particular system port is occupied or free.

---

# 33. Exit Codes

Preserve v0.1 semantics unless the new feature requires a clearly documented distinction.

Expected baseline:

```text
0 = requested operation succeeded and desired condition was satisfied
1 = one or more requested ports are in use / requested condition not satisfied
2 = invalid CLI input
3 = unexpected/system error
```

For `--find`, define whether failure to find a free port returns:

```text
1
```

or another code.

Prefer `1` because it represents the requested condition not being satisfied.

Document the decision.

---

# 34. Error Handling

Errors must remain concise.

Examples:

```text
error: invalid port range "3000-70000": port must be between 1 and 65535
```

```text
error: invalid port range "3000-1000": start port must not exceed end port
```

```text
error: --find requires exactly one starting port
```

```text
error: --quiet and --json cannot be used together
```

Avoid vague errors.

---

# 35. Output and stderr

Continue v0.1 behavior:

Successful results:

```text
stdout
```

Errors:

```text
stderr
```

For JSON mode, valid JSON results must go to stdout.

Errors related to command invocation must go to stderr.

Do not corrupt JSON output with diagnostic text.

---

# 36. Performance

v0.2 introduces potentially large ranges.

The implementation should be benchmarked enough to identify obvious performance problems.

At minimum consider:

```text
single port
100-port range
1000-port range
65535-port range
```

Do not optimize prematurely.

Do not add concurrency solely because range support exists.

If measurements show that large ranges are unreasonably slow, document the observation and consider a carefully bounded approach.

---

# 37. Memory

Range expansion should remain bounded by the TCP port space.

Avoid:

```text
range
→ duplicate []int
→ duplicate results
→ duplicate JSON structures
→ duplicate output strings
```

where simple streaming or reuse is possible.

However, do not sacrifice clarity for microscopic memory savings.

# 48. v0.2 Philosophy

v0.1 proved:

```text
Can Portcheck correctly inspect ports?
```

v0.2 should prove:

```text
Can Portcheck expose that capability as a reusable,
scriptable, structured developer tool?
```

The important architectural transition is:

```text
                 v0.1
                   │
             CLI application
                   │
                   ▼
             TCP checker
```

becoming:

```text
                 v0.2
                   │
          ┌────────┴────────┐
          │                 │
        CLI              Go API
          │                 │
          └────────┬────────┘
                   ▼
             Core checker
                   │
                   ▼
          Structured results
             /          \
          Human         JSON
```

The goal is not to make Portcheck dramatically larger.

The goal is to make the small core **reusable and composable** without sacrificing the simplicity established in v0.1.
