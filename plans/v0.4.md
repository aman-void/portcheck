# Portcheck v0.4

> Process inspection release: identify local processes associated with listening TCP ports while keeping the core networking layer portable and platform-independent.

---

# 1. Version Objective

Version `0.4.0` introduces local process inspection.

The primary new capability is:

> Given a local TCP port that is in use, identify the process associated with the listening socket where the operating system provides enough information to do so.

Example:

```bash
portcheck --process 8080
```

Expected conceptual output:

```text
PORT    STATUS
8080    IN USE

PROCESS
NAME    PID
api     18242
```

The exact process information available depends on the operating system and user permissions.

v0.4 must therefore introduce a platform-specific process inspection layer while keeping the core port-checking functionality portable.

---

# 2. Starting Point

v0.4 must begin from an accepted v0.3 implementation.

Before making changes:

```bash
go test ./...
go vet ./...
go build ./cmd/portcheck
```

If v0.3 is not healthy, fix the regression before implementing v0.4.

Do not build process inspection on top of a broken watch/wait/address implementation.

---


Process inspection is strictly read-only.

---

# 4. Core Safety Principle

Portcheck must **never modify or control processes**.

It may:

```text
read process information
read socket information
identify PID
identify process name
identify executable path
```

It must NOT:

```text
kill process
stop process
restart process
send signals
change process priority
modify process state
```

v0.4 is an inspection feature, not a process manager.

---

# 5. Architecture

The architecture should evolve into:

```text
                    CLI
                     │
                     ▼
              Application layer
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
    TCP port checker       Process inspector
          │                     │
          │             ┌───────┼────────┐
          │             ▼       ▼        ▼
          │           Linux   macOS   Windows
          │
          ▼
       Result
          │
          └──────────────┐
                         ▼
                  Combined result
                         │
                  ┌──────┴──────┐
                  ▼             ▼
               Human          JSON
```

The process layer must not become part of the core TCP checker.

---

# 6. Process Inspector Interface

Introduce a small internal abstraction.

Conceptually:

```go
type Inspector interface {
    Inspect(ctx context.Context, host string, port int) (ProcessInfo, error)
}
```

The exact interface may differ.

The important requirement is that:

```text
platform-independent code
        │
        ▼
process inspector abstraction
        │
        ├── Linux
        ├── macOS
        └── Windows
```

The platform-specific implementation must be isolated.

---

# 7. Process Information Model

A process result may contain:

```go
type ProcessInfo struct {
    PID        int
    Name       string
    Executable string
}
```

Not every platform will provide every field.

Fields should therefore have clear semantics.

For example:

```text
PID
    Process identifier.

Name
    Process name where available.

Executable
    Executable path where available.
```

If information cannot be obtained, do not invent it.

---

# 8. Optional Process Fields

A platform may provide:

```text
PID
Name
Executable
User
Command line
```

v0.4 should initially limit itself to:

```text
PID
Name
Executable
```

Do not add user ownership or command-line arguments unless they are required by the implementation and provide significant value.

The more process metadata you expose, the more platform-specific behavior becomes part of the public contract.

---

# 9. CLI Flag

Introduce:

```bash
portcheck --process 8080
```

The flag should request process information.

Without the flag:

```bash
portcheck 8080
```

behavior remains unchanged.

The default command must remain fast and simple.

---

# 10. Process Mode Semantics

If the port is free:

```bash
portcheck --process 8080
```

there is no process to report.

Example:

```text
PORT    STATUS
8080    FREE

PROCESS
none
```

Alternatively, process information can simply be omitted.

Prefer the cleaner output:

```text
PORT    STATUS
8080    FREE
```

No process section is necessary.

---

# 11. Occupied Port

When the port is in use:

```bash
portcheck --process 8080
```

should attempt process inspection.

Example:

```text
PORT    STATUS
8080    IN USE

PROCESS
PID         18242
NAME        yardly-api
EXECUTABLE  /usr/local/bin/yardly-api
```

The exact output should depend on which fields are available.

---

# 12. Multiple Ports

Process mode must work with multiple ports.

Example:

```bash
portcheck --process 3000 8080 5432
```

Output should preserve input order.

Example:

```text
PORT    STATUS

3000    FREE

8080    IN USE
        PID:  18242
        NAME: api

5432    IN USE
        PID:  938
        NAME: postgres
```

Keep the output readable.

Do not turn the terminal into a database query result.

---

# 13. Range Support

Process mode must work with v0.2 ranges.

Example:

```bash
portcheck --process 8000-8010
```

Each occupied port may have associated process information.

Do not assume every port maps to exactly one process.

---

# 14. Multiple Processes

A port may potentially be associated with more than one process due to:

- socket sharing
- platform behavior
- IPv4/IPv6 interactions
- inherited file descriptors
- special socket configurations

The process model must not blindly assume:

```text
one port = one PID
```

If multiple processes are discovered, represent them explicitly.

Potential model:

```go
type Result struct {
    Port      int
    Status    Status
    Processes []ProcessInfo
    Err       error
}
```

Do not change the public API casually.

If the existing public result model cannot cleanly represent this, design the v0.4 extension deliberately and document the compatibility impact.

---

# 15. Linux Implementation

Linux should be the primary OS-specific implementation for v0.4.

The implementation should use operating-system facilities to map listening TCP sockets to processes.

Possible sources include:

```text
/proc
```

and relevant socket information exposed by the operating system.

The implementation must not depend on external commands such as:

```text
lsof
ss
netstat
fuser
```

unless explicitly approved later.

The goal is a self-contained binary.

---

# 16. Linux `/proc` Considerations

Linux process inspection may require reading:

```text
/proc/<pid>/
```

and socket information.

The implementation must account for:

- processes disappearing during inspection
- permission restrictions
- inaccessible `/proc` entries
- stale socket information
- PID reuse
- malformed proc entries
- container environments
- namespaces where applicable

Do not assume `/proc` is perfectly stable.

The implementation should tolerate races gracefully.

---

# 17. Linux Permission Errors

A normal user may not be able to inspect every process.

For example, process metadata may be inaccessible because of:

```text
permissions
hidepid configuration
container isolation
security policies
```

The tool must not crash.

If the port is known to be in use but process identification fails, distinguish:

```text
Port status:
IN USE

Process:
unavailable
```

from:

```text
Port:
FREE
```

Never turn "couldn't inspect the process" into "port is free."

---

# 18. macOS Implementation

macOS process inspection should be implemented where practical using native OS facilities.

Do not assume Linux `/proc` exists.

The implementation must be isolated using Go build constraints or equivalent platform-specific files.

For example:

```text
internal/process/
├── process.go
├── process_linux.go
├── process_darwin.go
└── process_windows.go
```

If a platform cannot safely provide the requested information, return a clear unsupported/error result.

Do not fake compatibility.

---

# 19. Windows Implementation

Windows has fundamentally different process and socket inspection mechanisms.

The implementation should use appropriate Windows APIs where practical.

Do not shell out to:

```text
netstat
tasklist
PowerShell
```

for the core feature.

If Windows process mapping is too complex to implement safely in v0.4, the implementation may initially return an explicit unsupported result on Windows while preserving compilation and clean CLI behavior.

Do not produce false process information.

---

# 20. Platform Capability Model

Process inspection should have explicit capability semantics.

Possible states:

```text
supported
unsupported
permission_denied
not_found
error
```

This is preferable to returning an empty process object and making the caller guess what happened.

---

# 21. Process Not Found

A port may be reported as:

```text
IN USE
```

but process lookup may return no matching process.

This can happen because the process exited between socket inspection and process inspection.

This is a race condition, not necessarily an application failure.

The result should communicate:

```text
Port: IN USE
Process: unavailable
```

rather than changing the port state.

---

# 22. Process Race Conditions

The implementation must expect:

```text
check port
    ↓
port is in use
    ↓
process exits
    ↓
inspect process
    ↓
nothing found
```

This is normal in a live operating system.

Do not retry indefinitely.

A small bounded retry may be reasonable, but is not required.

---

# 23. Executable Path

If the operating system provides the executable path safely:

```text
Executable: /usr/local/bin/server
```

include it.

If unavailable:

```text
Executable: unavailable
```

or omit it.

Do not require executable paths for successful process identification.

---

# 24. Process Name

Process names should be treated as informational.

Examples:

```text
node
postgres
nginx
yardly-api
```

Do not rely on process names to identify a process uniquely.

PID is the authoritative process identifier.

---

# 25. PID

PID should be represented as an integer.

Example:

```json
{
  "pid": 18242
}
```

Do not represent PID as a string unless required by platform compatibility.

---

# 26. JSON Output

Extend the v0.2 JSON model.

Without process mode:

```json
{
  "port": 8080,
  "status": "in_use"
}
```

With process mode:

```json
{
  "port": 8080,
  "status": "in_use",
  "processes": [
    {
      "pid": 18242,
      "name": "yardly-api",
      "executable": "/usr/local/bin/yardly-api"
    }
  ]
}
```

Do not include `processes` for a free port unless the schema requires an explicit empty array.

Prefer consistent schema semantics.

---

# 27. JSON Error Representation

If the port is in use but process inspection fails:

```json
{
  "port": 8080,
  "status": "in_use",
  "process_error": "permission denied"
}
```

The exact field should be stable and documented.

Do not overwrite:

```text
status = in_use
```

with:

```text
status = error
```

when only process inspection failed.

The port check and process inspection are separate operations.

---

# 28. Quiet Mode

Define process behavior explicitly.

Recommended:

```bash
portcheck --process --quiet 8080
```

should continue to output only the status:

```text
IN_USE
```

Quiet mode should not suddenly print a PID.

If the user wants process details, they should use normal or JSON output.

---

# 29. Process Mode + Watch

v0.4 should support:

```bash
portcheck --process --watch 8080
```

but process information should only be emitted when the port state changes or process information changes.

Avoid repeatedly printing the same PID every polling interval.

Example:

```text
08:10:01  IN USE  PID=18242 NAME=api
08:10:05  FREE
08:10:08  IN USE  PID=19311 NAME=api
```

This is useful because the process occupying the port may change while the port remains occupied.

---

# 30. Process Changes While Port Remains Occupied

Watch mode should detect meaningful process changes.

Example:

```text
Port 8080:
IN USE by PID 1000
       ↓
Process exits
       ↓
IN USE by PID 2000
```

Even though:

```text
port state = IN USE
```

did not change, process ownership did.

In process-aware watch mode, emit the process transition.

---

# 31. Process Mode + Wait

Do not make process inspection a requirement for wait mode.

This should remain valid:

```bash
portcheck --wait 8080
```

Process information should only be requested when:

```bash
portcheck --wait --process 8080
```

If process information is requested, return the final process-aware state.

---

# 32. `--process` on Free Ports

Do not treat this as an error.

Example:

```bash
portcheck --process 8080
```

when free:

```text
PORT    STATUS
8080    FREE
```

Process inspection is simply unnecessary.

---

# 33. `--process` and `--find`

This combination needs explicit semantics.

Recommended:

```bash
portcheck --process --find 3000
```

finds the first free port.

Because the resulting port is free, there is no process to inspect.

The command should therefore return:

```text
3002
```

or the documented structured result.

Do not attempt to inspect a process on the free port.

---

# 34. `--process` and JSON

Must work:

```bash
portcheck --process --json 8080
```

The process fields should be represented structurally.

JSON consumers should not have to parse terminal text.

---

# 35. Process Information API

If process information becomes part of the public Go API, keep it minimal.

Potential:

```go
type ProcessInfo struct {
    PID        int
    Name       string
    Executable string
}
```

If platform capability needs to be represented, consider returning:

```go
ProcessInfo
error
```

rather than exposing a large platform-specific status hierarchy.

The public API should not expose `/proc` concepts.

---

# 36. Internal vs Public Process API

Prefer keeping the platform-specific process inspector internal initially.

For example:

```text
internal/process/
```

The public Portcheck API can expose stable process information without exposing:

```text
LinuxProcInspector
DarwinSocketScanner
WindowsHandleResolver
```

Those are implementation details.

---

# 37. Build Constraints

Use Go build constraints only for genuinely OS-specific implementations.

For example:

```text
process_linux.go
process_darwin.go
process_windows.go
```

Avoid scattering operating-system checks throughout unrelated code.

Bad:

```go
if runtime.GOOS == "linux" {
    ...
}
```

everywhere.

Prefer isolated platform files.

---

# 38. Unsupported Platforms

If process inspection is not implemented on a platform:

```bash
portcheck --process 8080
```

should produce a clear message such as:

```text
error: process inspection is not supported on this platform
```

or an equivalent structured result.

Do not fail the basic port-checking capability.

For example:

```text
portcheck 8080
```

must continue to work.

---

# 39. Cross-Compilation

The repository must continue to compile for supported platforms.

At minimum, verify builds for:

```text
linux/amd64
linux/arm64
darwin/amd64
darwin/arm64
windows/amd64
windows/arm64
```

where practical in the development environment.

Do not require executing platform-specific process inspection tests on an OS that is not available.

---

# 40. Testing Strategy

Process inspection tests require more care than ordinary port tests.

Do not hardcode:

```text
PID 1234
```

or assume a specific process is listening.

Tests should create controlled listeners where possible.

---

# 41. Linux Process Tests

On Linux:

1. Start a TCP listener in the test process.
2. Determine its dynamically assigned port.
3. Run process inspection.
4. Verify that the current process or expected process can be identified.
5. Verify PID where reliable.
6. Verify process name where reliable.
7. Close the listener.
8. Verify behavior after closure.

Be careful about PID matching if the test process and listener are in the same process.

---

# 42. Process Race Tests

Test the case where:

```text
port is occupied
process exits
inspection happens
```

The expected behavior is not necessarily a process result.

The important requirement is:

```text
no panic
no incorrect FREE result
no infinite retry
```

---

# 43. Permission Tests

Permission behavior may be difficult to reproduce reliably.

Tests should not require special root privileges.

Where permission-denied behavior cannot be deterministically reproduced, isolate it as platform-specific behavior rather than making the entire suite depend on it.

---

# 44. JSON Process Tests

Decode JSON and verify:

```text
port
status
processes
pid
name
executable
```

where supported.

Do not compare raw JSON strings.

---

# 45. Watch Process Tests

Test:

```text
port becomes occupied by process A
    ↓
process A information emitted
    ↓
process A exits
    ↓
port becomes occupied by process B
    ↓
process B information emitted
```

Avoid long sleeps.

Use controlled synchronization where possible.

---

# 46. Regression Tests

All existing tests must continue to pass:

```bash
go test ./...
```

Do not remove tests because process inspection changed result structures.

Update tests intentionally if the public schema has evolved.

---

# 47. Error Handling

Process errors should not obscure port status.

Bad:

```text
error: process inspection failed
```

when the actual useful information is:

```text
8080 IN USE
process unavailable: permission denied
```

The port state and process state are separate.

---

# 48. Security Considerations

Process inspection reads sensitive operating-system metadata.

Do not:

- execute arbitrary commands
- follow untrusted paths blindly
- expose unnecessary command-line arguments
- read unrelated process files
- modify process state

Only retrieve information needed for:

```text
PID
name
executable
```

and only when the user explicitly requests process inspection.

---

# 49. No External Commands

The core process inspection implementation must not depend on:

```text
lsof
ss
netstat
fuser
tasklist
PowerShell
```

This would undermine the project's dependency-free and portable design.

If a platform-specific implementation genuinely cannot be completed without external commands, report the limitation rather than silently adding one.

---

# 50. Performance

Process inspection can be considerably more expensive than a simple TCP bind.

Therefore:

```bash
portcheck 8080
```

must remain fast.

Only perform process inspection when:

```bash
--process
```

is explicitly supplied.

Do not automatically inspect processes for every normal port check.

---

# 51. Caching

Do not introduce process-result caching in v0.4.

Process information can change rapidly.

If watch mode requires repeated inspection, perform it when necessary.

Optimization can be considered later based on measurement.

---

# 60. v0.4 Philosophy

The progression is now:

```text
v0.1
    Can we check a TCP port?

v0.2
    Can we make the result reusable and scriptable?

v0.3
    Can we observe and wait for port state?

v0.4
    Can we explain what process is responsible?
```

The architectural principle is:

> **OS-specific knowledge belongs at the edge of the system, not inside the core port-checking engine.**

The desired architecture is:

```text
                 Portcheck
                     │
          ┌──────────┴──────────┐
          │                     │
     Portable core          OS-specific edge
          │                     │
     TCP checking       Process inspection
          │               /      |      \
          │            Linux   macOS   Windows
          │
          └──────────┬──────────┘
                     ▼
              Structured result
                     │
                CLI / JSON
```

If v0.4 achieves that separation cleanly, v0.5 can build connectivity and diagnostics on top of it without turning the codebase into platform-specific spaghetti.
