# Portcheck v0.3

> Monitoring release: explicit address selection, watch mode, wait mode, cancellation, and improved long-running CLI behavior.

---

# 1. Version Objective

Version `0.3.0` extends Portcheck from a one-shot port inspection tool into a lightweight local port monitoring utility.

The primary capabilities introduced are:

- explicit host/address selection
- watch mode
- state-change monitoring
- wait-until-available
- wait-until-in-use
- cancellation
- configurable polling interval
- clean handling of long-running operations

The existing v0.1 and v0.2 functionality must remain compatible unless explicitly changed by this specification.

---

# 2. Starting Point

v0.3 must begin from an accepted v0.2 implementation.

Before modifying the project, run:

```bash
go test ./...
go vet ./...
go build ./cmd/portcheck
```

If v0.2 is broken, resolve the regression before implementing v0.3 functionality.

Do not build new features on top of an unhealthy codebase.

# 4. Design Goals

v0.3 changes the conceptual model from:

```text id="3bq2fn"
Check once
```

to:

```text id="k6w74v"
Check
  │
  ├── once
  │
  ├── repeatedly
  │
  └── until condition
```

The underlying checker should remain stateless.

Long-running behavior belongs in the application/use-case layer.

# 5. Address Selection

v0.1 and v0.2 check:

```text id="8yd5h3"
127.0.0.1:<port>
```

v0.3 introduces:

```bash id="gqjxx2"
portcheck --host 127.0.0.1 8080
```

The host/address must be configurable.

Examples:

```bash id="7dfj9s"
portcheck --host 127.0.0.1 8080
```

```bash id="jcrp3r"
portcheck --host 0.0.0.0 8080
```

```bash id="50b9ov"
portcheck --host ::1 8080
```

The host should represent an IP address or hostname accepted by the Go networking layer, subject to the semantics documented below.

---

# 6. Default Host

For backward compatibility, if `--host` is not supplied:

```text id="k0w9m2"
127.0.0.1
```

must remain the default.

Therefore:

```bash id="d2e2m9"
portcheck 8080
```

continues to behave like:

```bash id="pg0y7v"
portcheck --host 127.0.0.1 8080
```

Existing scripts must not change behavior.

---

# 7. Address Semantics

The tool must clearly distinguish:

```text id="6hcvxz"
localhost
specific local address
wildcard address
hostname
```

Do not claim that checking:

```text id="qj9mbm"
127.0.0.1:8080
```

proves that:

```text id="2nq6l5"
0.0.0.0:8080
```

is free.

Binding behavior is operating-system dependent.

The README must document that address selection affects what "free" means.

---

# 8. Host Validation

Invalid host/address input should produce a useful error.

Examples:

```text id="slm4f0"
empty host
malformed IP address
invalid address syntax
```

Do not perform unnecessary DNS resolution merely to validate a host if the operation itself can handle it.

For local binding, hostname semantics must be carefully defined.

The implementation must not silently check a different address than the user requested.

---

# 9. Address + Port Construction

Do not construct addresses using naive string concatenation such as:

```go
address := host + ":" + strconv.Itoa(port)
```

This breaks IPv6.

Use the appropriate standard-library mechanism, such as:

```go
net.JoinHostPort(host, strconv.Itoa(port))
```

This must correctly produce:

```text id="9x5y1b"
127.0.0.1:8080
[::1]:8080
```

---

# 10. API Evolution

The v0.2 API should be extended carefully.

Avoid breaking:

```go id="qkpnvy"
Check(ctx, 8080)
```

unless there is a compelling reason.

A possible API evolution is:

```go id="7w8j20"
Check(ctx, CheckOptions{
    Host: "127.0.0.1",
    Port: 8080,
})
```

or a similarly small options-based design.

The exact API is an implementation decision.

The agent must prioritize:

- backward compatibility
- clear semantics
- small public API
- avoiding excessive option structures

Do not introduce a giant configuration object for three fields.

---

# 11. Watch Mode

Introduce:

```bash id="z96hl7"
portcheck --watch 8080
```

The command repeatedly checks the port.

Example:

```text id="2az9jr"
Port 8080
Watching...

17:20:01  IN USE
17:20:03  IN USE
17:20:05  FREE
17:20:07  FREE
```

However, repeated identical states should not necessarily be printed.

The preferred behavior is **state-change output**.

Example:

```text id="e4k1sh"
17:20:01  IN USE
17:20:05  FREE
17:20:07  IN USE
```

---

# 12. Watch Mode State Changes

The watcher should conceptually maintain:

```text id="zgjpab"
previous state
      │
      ▼
perform check
      │
      ▼
compare with previous
      │
      ├── same → no state output
      │
      └── changed → output transition
```

This prevents terminal spam.

Do not print the same state every polling interval unless an explicit future option requests that behavior.

---

# 13. Initial Watch State

When watch mode starts, the current state should be emitted immediately.

Example:

```bash id="y2z0p1"
portcheck --watch 8080
```

Output:

```text id="a7qjhm"
17:20:01  IN USE
```

Then only changes are printed.

The user should not have to wait for the first state transition to know the current state.

---

# 14. Watch Timestamp

Watch output should include timestamps.

Use a stable human-readable format.

Example:

```text id="8tj2vy"
15:04:05
```

The exact format may be:

```text id="qg5jla"
2006-01-02 15:04:05
```

if full timestamps are preferred.

Keep the output readable.

Do not add a timestamp library.

Use Go's standard `time` package.

---

# 15. Watch Multiple Ports

v0.3 should support watching multiple ports.

Example:

```bash id="e5i1b8"
portcheck --watch 3000 8080
```

Output might be:

```text id="qxw0lz"
15:20:01  3000 FREE
15:20:01  8080 IN USE
15:20:05  8080 FREE
```

The exact formatting should remain simple.

Each port maintains its own previous state.

---

# 16. Watch + Range

Because v0.2 supports ranges, watch mode should operate on the expanded set of ports.

Example:

```bash id="6c9avw"
portcheck --watch 3000-3003
```

Each unique port should be monitored.

Do not create a separate range-monitoring implementation.

Reuse the existing input expansion logic.

---

# 17. Watch + JSON

v0.3 must define how JSON interacts with watch mode.

Recommended behavior:

```bash id="ecy1e9"
portcheck --watch --json 8080
```

should produce newline-delimited JSON events.

Example:

```json id="afcgy7"
{"timestamp":"2026-10-01T08:10:00+05:45","port":8080,"status":"in_use"}
{"timestamp":"2026-10-01T08:10:05+05:45","port":8080,"status":"free"}
```

This is preferable to repeatedly printing a JSON array.

The format should be documented as an event stream.

If the implementation determines that JSON watch mode creates unnecessary complexity, it may reject the combination instead.

However, supporting structured event output is preferred because it makes watch mode useful for automation.

---

# 18. Watch Polling Interval

Repeated checking requires a polling interval.

Introduce:

```bash id="d2f7sk"
portcheck --watch --interval 2s 8080
```

The interval must be positive.

Examples:

```text id="7fgzck"
500ms
1s
2s
5s
10s
```

Use Go's standard duration parsing.

---

# 19. Default Polling Interval

If no interval is specified, use a sensible default.

Recommended:

```text id="4n1o8y"
1 second
```

The default should be documented.

Do not poll as fast as possible.

A tight loop such as:

```go
for {
    check()
}
```

is unacceptable.

It would waste CPU and potentially stress the operating system.

---

# 20. Minimum Polling Interval

The implementation may enforce a reasonable lower bound.

For example:

```text id="0l11ki"
100ms
```

The exact value should be chosen based on simplicity and actual behavior.

Do not create a complicated rate limiter.

The primary requirement is to prevent accidental busy loops.

---

# 21. Watch Cancellation

Watch mode must terminate cleanly when the user presses:

```text id="v3j5j5"
Ctrl+C
```

The application should respond to `SIGINT`.

Use:

```go id="a6f3w8"
os/signal
signal.NotifyContext
```

or the appropriate standard-library mechanism.

Do not leave goroutines running after cancellation.

---

# 22. Watch Exit Behavior

When watch mode is interrupted by the user:

- terminate cleanly
- do not print a scary error
- return an appropriate exit status

Recommended:

```text id="6bq6g3"
Ctrl+C → exit 0
```

This represents normal user termination rather than failure.

---

# 23. Wait Mode

Introduce:

```bash id="0hn6ap"
portcheck --wait 8080
```

This means:

> Keep checking until the port becomes free.

Example:

```text id="nqzquj"
Waiting for port 8080 to become FREE...
```

Once it becomes free:

```text id="gl3hju"
8080 FREE
```

Then exit successfully.

---

# 24. Wait-Until-In-Use

Also support:

```bash id="d9r1b6"
portcheck --wait-in-use 8080
```

This means:

> Keep checking until the port becomes occupied.

Example:

```text id="xj8j3w"
Waiting for port 8080 to become IN USE...
```

Then:

```text id="6onq5y"
8080 IN USE
```

Exit successfully.

---

# 25. Wait Polling

Wait mode should use the same polling interval system as watch mode.

Example:

```bash id="0o0bkl"
portcheck --wait --interval 500ms 8080
```

The default should remain:

```text id="vqmuxo"
1 second
```

Do not duplicate polling implementations.

---

# 26. Wait Cancellation

Wait mode must respond to Ctrl+C.

Example:

```text id="a4tr90"
Waiting for port 8080...
^C
```

The program should terminate cleanly.

Do not leave timers, goroutines, or listeners behind.

---

# 27. Wait Timeout

v0.3 should support an optional timeout.

Example:

```bash id="u1xg3d"
portcheck --wait --timeout 30s 8080
```

If the condition is not reached:

```text id="j5sgt5"
error: timeout waiting for port 8080 to become FREE
```

The command should return a non-zero status.

A reasonable exit code is:

```text id="0m0tmi"
1
```

because the requested condition was not satisfied.

---

# 28. Timeout Validation

Reject:

```text id="t6q9w7"
--timeout 0
--timeout -1s
```

Accept:

```text id="njl8l2"
1s
500ms
30s
5m
```

Use Go duration parsing.

Do not implement custom duration syntax.

---

# 29. Watch Timeout

Do not introduce a separate watch timeout unless there is a concrete need.

Watch mode is inherently long-running.

v0.3 should focus on:

```text id="l8a9y5"
--watch
--interval
Ctrl+C
```

A future version may introduce bounded monitoring if needed.

---

# 30. Wait and Watch Exclusivity

Do not allow contradictory modes.

Examples that should be rejected:

```bash id="2z9f41"
portcheck --watch --wait 8080
```

```bash id="a0o5uv"
portcheck --watch --wait-in-use 8080
```

```bash id="l5o0fn"
portcheck --wait --wait-in-use 8080
```

Return a clear CLI error.

One operation should have one clear semantic.

---

# 31. `--wait` and `--wait-in-use`

Treat these as mutually exclusive modes.

The semantics are:

```text id="t7yl0f"
--wait
    wait until every requested port is FREE

--wait-in-use
    wait until every requested port is IN USE
```

For multiple ports, the condition should be clearly documented.

Recommended:

```text id="u8yk5f"
ALL requested ports must reach the desired state.
```

Example:

```bash id="9q2qjg"
portcheck --wait 3000 8080
```

returns only when:

```text id="d0m1tr"
3000 FREE
AND
8080 FREE
```

Do not return when only one port changes.

---

# 32. Wait + Range

Wait mode should work with v0.2 ranges.

Example:

```bash id="3e4x8a"
portcheck --wait 3000-3003
```

The command waits until every requested port is free.

Likewise:

```bash id="ef3nqk"
portcheck --wait-in-use 3000-3003
```

waits until every requested port is occupied.

---

# 33. Wait + JSON

Wait mode should produce the final state as JSON if requested.

Example:

```bash id="q4w8ry"
portcheck --wait --json 8080
```

After the condition is satisfied:

```json id="l4k6on"
[
  {
    "port": 8080,
    "status": "free"
  }
]
```

Do not emit repeated polling results in normal JSON wait mode.

Watch mode is the event-stream use case.

---

# 34. Address + Watch

Host selection must work with watch mode.

Example:

```bash id="0xv5co"
portcheck --host 127.0.0.1 --watch 8080
```

The host must remain constant throughout the watch operation.

---

# 35. Address + Wait

Likewise:

```bash id="4kqj5d"
portcheck --host 127.0.0.1 --wait 8080
```

The check must use the requested address on every polling attempt.

---

# 36. Address + Find

`--find` from v0.2 must also respect the selected host.

Example:

```bash id="cl8t8f"
portcheck --host 127.0.0.1 --find 3000
```

The tool must find a port that is free on the specified host/address.

Do not silently revert to `127.0.0.1`.

---

# 39. Suggested Library Abstractions

A possible long-term API:

```go id="8f0cy0"

```


# 40. Watch Architecture

A reasonable internal model is:

```text id="4c7c8c"
               Context
                  │
                  ▼
            Watch loop
                  │
          ┌───────┴────────┐
          ▼                ▼
       ticker            cancel
          │                │
          ▼                ▼
       Check           terminate
          │
          ▼
   Compare previous
          │
          ▼
     State changed?
       /        \
     yes         no
      │           │
    output       wait
```

The implementation should avoid busy loops.

---

# 41. Polling Implementation

Use:

```go id="u0m4pp"
time.NewTicker(interval)
```

or an equivalent standard-library approach.

Always stop timers/tickers appropriately.

Do not allocate a new ticker every iteration.

Do not sleep blindly if context cancellation must be responsive.

Prefer cancellation-aware waiting.

---

# 42. Concurrency

v0.3 does not require concurrency.

Watch mode with multiple ports can initially check ports sequentially within each polling cycle.

Example:

```text id="m0nqbg"
tick
 ↓
check 3000
 ↓
check 3001
 ↓
check 3002
 ↓
sleep until next tick
```

If performance becomes an issue, measure first.

Do not add a worker pool by default.

---

# 43. Error Handling During Watch

Transient errors should not necessarily terminate the entire watch.

For example, if one check temporarily returns an unexpected system error:

```text id="w8w3r6"
3000 ERROR: ...
```

the implementation should decide whether the error is:

- transient
- fatal
- a state transition

The behavior must be deterministic and documented.

Do not silently convert an error into `FREE` or `IN USE`.

---

# 44. Error Handling During Wait

If a check encounters an unexpected system error:

```text id="r9p5gf"
error: failed to check 127.0.0.1:8080: ...
```

the wait operation should normally terminate rather than blindly retrying an unknown failure forever.

A future version may distinguish retryable errors.

v0.3 should prefer correctness and predictable failure.

---

# 45. JSON Watch Events

If JSON watch mode is implemented, use a stable event structure.

Example:

```json id="q3m5bc"
{
  "timestamp": "2026-10-01T08:10:00+05:45",
  "host": "127.0.0.1",
  "port": 8080,
  "status": "in_use"
}
```

Use RFC3339 timestamps.

Each state-change event should be one JSON object per line.

This makes the output stream compatible with tools such as:

```bash id="y0f8py"
jq
```

# 63. Human Review Gate

Before accepting v0.3, inspect the implementation carefully.

Pay particular attention to:

```text id="4j3f8x"
Does Ctrl+C actually terminate everything?
Are tickers stopped?
Are goroutines leaked?
Does watch mode spam output?
Are IPv6 addresses handled correctly?
Does --host actually affect every check?
Does --wait cancel correctly?
Does timeout work?
Are conflicting flags rejected?
Does JSON remain valid?
Did the agent accidentally introduce OS-specific code?
```

Long-running code is where small mistakes stop being cute.

Also inspect whether the agent has created a giant abstraction for watch mode.

The ideal implementation should still be understandable by a developer reading the repository months later.

# 64. v0.3 Philosophy

v0.1 established:

```text
Can we correctly inspect a port?
```

v0.2 established:

```text
Can the functionality be reused and consumed programmatically?
```

v0.3 establishes:

```text
Can Portcheck observe and wait for network state
without becoming a complicated monitoring system?
```

The architectural progression is:

```text id="b2f5u4"
v0.1
   │
   ▼
One-shot checking
   │
   ▼
v0.2
   │
   ├── ranges
   ├── JSON
   └── Go API
   │
   ▼
v0.3
   │
   ├── address selection
   ├── watch
   ├── wait
   ├── timeout
   └── cancellation
```

The central principle remains:

> **The checker answers what the current state is. Higher-level code decides whether to check once, repeatedly, or until a condition is satisfied.**

That separation is what keeps the project from turning into a pile of special cases as the features grow.
