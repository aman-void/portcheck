# Portcheck v0.5 Implementation Plan

## 1. Purpose

Portcheck v0.5 introduces **connectivity testing and diagnostics**.

Until v0.4, Portcheck primarily answers:

> “Can this TCP port be bound, and what local process is associated with it?”

v0.5 adds:

> “Can I establish a TCP connection to this endpoint, and what does the result tell me?”

This release should make Portcheck useful for both local development and basic network troubleshooting while keeping the implementation small, deterministic, and standard-library-only.

The central principle remains:

> **Measure what actually happened. Do not invent a diagnosis beyond the available evidence.**

For example:

- `connection refused` means the TCP connection attempt was refused.
- It does **not** automatically mean “the server is broken.”
- `timeout` means the connection attempt did not complete within the configured timeout.
- It does **not** prove that a firewall caused the timeout.

---

# 2. Starting Point

v0.5 starts from an accepted v0.4 implementation.

Before changing anything, the agent MUST verify that the existing implementation passes:

```bash
gofmt -w .
go test ./...
go vet ./...
go build ./...
```

Existing v0.1-v0.4 behavior must remain intact unless this plan explicitly changes it.

# 3. v0.5 Goals

Implement:

1. TCP connectivity testing
2. Hostname resolution through Go's networking stack
3. IPv4 and IPv6 connectivity
4. Connection timeout handling
5. Structured connectivity results

- ICMP/ping
- traceroute
- packet capture

- subnet scanning
- port scanning
- service fingerprinting

- HTTP health checks

- SSH-specific checks

- automatic retries
- service restart

- firewall modification

- packet-level diagnostics
- remote process inspection
- cloud-provider diagnostics
- AI-generated diagnosis
- package managers
- Homebrew
- AUR
- npm
- release automation

v0.5 is a **TCP connectivity and local diagnostic release**, not a general network troubleshooting framework.

# 5. Core Concept: Availability vs Connectivity

This distinction is critical.

Portcheck already has a concept similar to:

```text
FREE
IN USE
```

That answers a local binding question:

> “Can this process bind this address and port?”

Connectivity answers a different question:

```text
REACHABLE
REFUSED
TIMEOUT
ERROR
```

That answers:

> “Could Portcheck establish a TCP connection to this endpoint?”

These concepts MUST NOT be mixed.

For example:

```text
Port availability:
IN USE

Connectivity:
REACHABLE
```

is perfectly valid.

Likewise:

```text
Port availability:
FREE

Connectivity:
REFUSED
```

can also be valid.

A local port may be unavailable for binding while the corresponding endpoint is not reachable from the testing location.

---

# 6. Connectivity Command

Add:

```bash
portcheck --connect <host:port>
```

Example:

```bash
portcheck --connect localhost:8080
```

```bash
portcheck --connect example.com:443
```

IPv6:

```bash
portcheck --connect '[::1]:8080'
```

The command performs a TCP connection attempt.

It should:

1. Parse the endpoint.
2. Validate the port.
3. Create a context with the configured timeout.
4. Attempt a TCP connection.
5. Close the connection immediately after successful establishment.
6. Convert the result into a structured connectivity result.
7. Render the result.

Do not send application data.

This is strictly a TCP connection test.

---

# 7. Endpoint Parsing

Use Go's networking primitives.

Prefer:

```go
net.SplitHostPort()
```

Do not manually parse:

```text
host:port
```

with string splitting.

IPv6 must work correctly.

Valid examples:

```text
localhost:8080
127.0.0.1:8080
example.com:443
[::1]:8080
```

Invalid examples should be rejected:

```text
localhost
localhost:
:8080
localhost:abc
localhost:0
localhost:65536
[::1]:99999
```

The implementation should distinguish:

- malformed endpoint
- invalid port
- DNS resolution failure
- connection failure

where practical.

---

# 8. Timeout

Reuse the existing `--timeout` concept introduced in v0.3.

Example:

```bash
portcheck --connect localhost:8080 --timeout 2s
```

The timeout applies to the connectivity attempt.

If no timeout is explicitly provided, use a reasonable finite default.

Recommended:

```text
5 seconds
```

The exact default should be defined as a named constant rather than scattered through the code.

Example conceptual constant:

```go
const defaultConnectTimeout = 5 * time.Second
```

Do not create a global configurable settings framework merely for this.

---

# 9. Context Cancellation

Connectivity operations must respect `context.Context`.

Conceptually:

```go
func Connect(ctx context.Context, address string, timeout time.Duration) Result
```

The implementation should use:

```go
net.Dialer.DialContext(...)
```

rather than manually managing blocking operations.

Ctrl+C should cancel the active operation.

The CLI must not remain stuck indefinitely after cancellation.

---

# 10. Connectivity Result

Introduce a structured internal result.

Conceptually:

```go
type ConnectivityStatus string

const (
    ConnectivityReachable ConnectivityStatus = "reachable"
    ConnectivityRefused   ConnectivityStatus = "refused"
    ConnectivityTimeout   ConnectivityStatus = "timeout"
    ConnectivityError     ConnectivityStatus = "error"
)
```

The exact naming can differ if the existing codebase has a better convention.

A result should contain enough information for both human and JSON output.

Conceptually:

```go
type ConnectivityResult struct {
    Address    string
    Status     ConnectivityStatus
    Duration   time.Duration
    Error      error
}
```

Do not expose implementation-specific networking errors as the primary API contract.

The structured status should remain stable even if the underlying operating-system error wording changes.

---

# 11. Connectivity Classification

At minimum, distinguish:

### Reachable

The TCP connection was successfully established.

```text
REACHABLE
```

### Refused

The connection attempt was explicitly refused.

Typically represented by:

```text
connection refused
```

The implementation may use Go's wrapped network errors to classify this.

Do not classify every error as `REFUSED`.

### Timeout

The operation exceeded its configured deadline.

```text
TIMEOUT
```

### Error

Other failures:

- DNS resolution errors
- invalid network configuration
- unreachable network
- address errors
- cancellation
- other unexpected failures

Do not pretend these are all equivalent.

Where useful, preserve the underlying error as diagnostic information.

---

# 12. Error Classification Rule

The implementation should prefer Go's standard error inspection mechanisms.

Use mechanisms such as:

```go
errors.Is()
```

and:

```go
errors.As()
```

where appropriate.

Do not compare error strings such as:

```go
if err.Error() == "connection refused" {
    ...
}
```

Error messages vary between operating systems and environments.

---

# 13. Duration

A successful connectivity result should record how long the TCP connection attempt took.

Example human output:

```text
ADDRESS              STATUS      LATENCY
localhost:8080       REACHABLE   0.42ms
```

The duration is informational.

Tests MUST NOT depend on an exact duration.

For example, this is bad:

```go
if result.Duration != 420*time.Microsecond {
    t.Fatal(...)
}
```

Instead test properties such as:

```text
duration >= 0
```

or simply verify that a duration was recorded.

---

# 14. Human Output

A simple connectivity check should remain compact.

Example:

```text
ADDRESS              STATUS
localhost:8080       REACHABLE
```

For useful diagnostic information:

```text
ADDRESS              STATUS      LATENCY
localhost:8080       REACHABLE   0.42ms
```

For refusal:

```text
ADDRESS              STATUS
localhost:49152      REFUSED
```

For timeout:

```text
ADDRESS              STATUS
10.0.0.10:8080       TIMEOUT
```

For an unexpected error:

```text
ADDRESS              STATUS
example.invalid:443  ERROR
ERROR                lookup example.invalid: no such host
```

Keep normal successful output concise.

---

# 15. Quiet Mode

Existing `--quiet` behavior must remain meaningful.

For connectivity:

```bash
portcheck --connect localhost:8080 --quiet
```

should output only the status:

```text
REACHABLE
```

or:

```text
REFUSED
```

or:

```text
TIMEOUT
```

or:

```text
ERROR
```

Do not print latency in quiet mode.

Connectivity must support the existing:

```bash
--json
```

flag.

Example:

```json
{
  "address": "localhost:8080",
  "status": "reachable",
  "duration_ms": 0.42

```

Refused:

```json
{
  "address": "localhost:49152",
  "status": "refused",
  "duration_ms": 0.31

```

Timeout:

```json
{
  "address": "10.0.0.10:8080",
```

```json
{
  "address": "example.invalid:443",
  "status": "error",
  "error": "..."
```

The `error` field should contain human-readable diagnostic information.

# 17. JSON Stability

Once introduced, the connectivity JSON structure becomes part of Portcheck's compatibility surface.

Use stable field names:

```text
address
status
duration_ms
error
```

Optional fields should be omitted when they do not apply.

For example, a successful result does not need:

```json
"error": null
```

unless the existing project JSON conventions require it.

Follow the conventions already established in v0.2-v0.4.

# 18. Connectivity API

If v0.2 introduced a public Go API, v0.5 may extend it with a small connectivity API.

Keep it intentionally minimal.

Conceptually:

```go
func Connect(ctx context.Context, address string) ConnectivityResult
```

or an equivalent API using explicit options.

Avoid exposing:

- `net.Dialer`
- platform-specific errors
- internal retry mechanisms
- CLI configuration types
- output formatting types

The public API should describe **what Portcheck does**, not how the CLI happens to implement it.

Do not introduce a large configuration object such as:

```go
PortcheckConfigurationEverything
```

for one operation.

# 19. Doctor Mode

Add a diagnostic mode:

```bash
portcheck doctor <port>
```

The purpose of `doctor` is to combine information already available inside Portcheck and present it as a useful factual diagnostic report.

Example:

```bash
portcheck doctor 8080
```

Conceptual output:

```text
Portcheck Doctor

Endpoint
  Host:     127.0.0.1
  Port:     8080
  Protocol: TCP

Local Port
  Status:   IN USE

Process
  PID:      18242
  Name:     yardly-api
  Executable: /usr/local/bin/yardly-api

Connectivity
  Status:   REACHABLE
  Latency:  0.41ms
```

The exact formatting can be refined during implementation.

---

# 20. Doctor Responsibilities

`doctor` may combine:

1. Host/address information
2. TCP local availability
3. Process inspection
4. TCP connectivity
5. Timing information
6. Clearly separated errors or unavailable capabilities

It should NOT attempt to magically determine:

```text
"Your firewall is broken."
```

or:

```text
"Your application has a bug."
```

unless there is actual evidence for such a statement.

Portcheck is a diagnostic tool, not a fortune teller.

---

# 21. Doctor Host Support

Support the existing host mechanism.

Example:

```bash
portcheck doctor --host 127.0.0.1 8080
```

and:

```bash
portcheck doctor --host ::1 8080
```

Use:

```go
net.JoinHostPort()
```

for endpoint construction.

Never construct addresses using:

```go
host + ":" + port
```

because IPv6 exists specifically to punish casual string concatenation.

---

# 22. Doctor Process Information

If the port is in use and process inspection is supported:

```text
Process
  PID:          18242
  Name:         yardly-api
  Executable:   /usr/local/bin/yardly-api
```

If process inspection is unavailable:

```text
Process
  Status:       unavailable
  Reason:       permission denied
```

If the port is free:

```text
Process
  Status:       none
```

Never fabricate process information.

---

# 23. Doctor Connectivity

Doctor should perform a TCP connection test against the selected endpoint.

For example:

```text
Connectivity
  Status:   REACHABLE
  Latency:  0.42ms
```

If the port is locally in use but connectivity fails:

```text
Local Port
  Status:   IN USE

Connectivity
  Status:   REFUSED
```

This is valuable because the two observations are different.

Do not collapse them into a single:

```text
BROKEN
```

status.

---

# 24. Doctor Diagnosis

A diagnostic summary may explain observed facts.

Example:

```text
Diagnosis
  A process is associated with this local port and the TCP endpoint
  accepted a connection.
```

For a free port:

```text
Diagnosis
  No local process is currently associated with this port.
  The TCP connection attempt was refused.
```

These messages must remain evidence-based.

Avoid speculative explanations such as:

```text
Your firewall is blocking traffic.
```

unless Portcheck has actually implemented firewall inspection, which is explicitly out of scope for v0.5.

# 29. No Shell Commands

Connectivity and diagnostics MUST NOT execute:

```text
ping
nc
telnet
curl
wget
ss
netstat
lsof
fuser
traceroute
```

or equivalent external commands.

Use Go's standard library.

This is especially important for the project goal of producing a portable Go binary.

# 30. Local Connectivity Testing

Tests must primarily use local TCP listeners.

Example strategy:

1. Start a TCP listener on:

```text
127.0.0.1:0
```

2. Read the dynamically assigned port.
3. Run the connectivity checker against it.
4. Assert:

```text
REACHABLE
```

5. Close the listener.
6. Run the checker again.
7. Assert:

```text
REFUSED
```

This avoids depending on:

- internet access
- DNS availability
- external servers
- CI network configuration

Tests should remain deterministic.

---

# 31. Timeout Testing

Timeout tests are difficult to make portable if they depend on arbitrary unreachable IP addresses.

Do NOT write a test that assumes:

```text
10.255.255.1
```

will always timeout.

That may behave differently across operating systems, networks, containers, VPNs, and CI environments.

Instead, design the connectivity implementation so its dialing operation can be controlled in unit tests.

An internal abstraction may be used if necessary.

For example, conceptually:

```go
type dialFunc func(ctx context.Context, network, address string) (net.Conn, error)
```

The production implementation uses:

```go
net.Dialer
```

Tests can inject deterministic behavior.

Keep such abstractions internal.

Do not expose them as public API.

---

# 32. Cancellation Testing

Test that cancellation is respected.

Conceptually:

1. Create a canceled context.
2. Start a connectivity operation.
3. Ensure it terminates promptly.
4. Verify the returned result represents cancellation appropriately.

Do not use long sleeps.

Tests should complete quickly.

---

# 33. DNS Testing

Avoid requiring external DNS infrastructure.

Test malformed addresses and controlled local addresses.

If hostname resolution behavior is tested, use stable local names such as:

```text
localhost
```

Do not require:

```text
google.com
example.com
```

to be reachable from CI.

---

# 34. IPv4 Tests

At minimum, verify:

```text
127.0.0.1:<dynamic-port>
```

works when IPv4 is available.

Do not assume IPv4 is universally configured if the test environment can disable it.

---

# 35. IPv6 Tests

Where the environment supports IPv6, test:

```text
[::1]:<dynamic-port>
```

Tests should detect unsupported IPv6 environments and avoid failing solely because IPv6 is unavailable.

Do not silently treat IPv6 as universally guaranteed.

---

# 36. Doctor Tests

Doctor tests should combine controlled components.

Test at least:

### Free port

Expected:

```text
Local: FREE
Process: none
Connectivity: REFUSED
```

### Active listener

Expected:

```text
Local: IN USE
Connectivity: REACHABLE
```

and process information where the platform implementation supports it.

### Process inspection failure

Verify:

```text
Local: IN USE
Process: unavailable
```

while connectivity remains independently reported.

### Process disappears

Simulate or reproduce the normal race where a process exits between:

```text
port detection
```

and:

```text
process inspection
```

The doctor command should still return a coherent report.

# 37. CLI Mode Conflicts

v0.5 must preserve existing validation of incompatible modes.

Connectivity should not silently combine with unrelated modes.

For example, reject combinations such as:

```bash
portcheck --connect localhost:8080 3000
```

unless the implementation explicitly defines multi-mode semantics.

Prefer rejecting ambiguous combinations.

Similarly, do not allow:

```bash
portcheck --connect localhost:8080 --watch
```

unless watch connectivity has been deliberately designed.

For v0.5, **do not implement connectivity watch mode**.

Keep watch behavior from v0.3 unchanged for local port checks.

# 38. `--connect` and `--process`

Do not automatically combine:

```bash
--connect
```

with:

```bash
--process
```

because `--connect` may target a remote host where local process inspection makes no sense.

If process inspection is needed for diagnostics, use:

```bash

```

where the semantics are explicit.

# 40. Exit Codes

Preserve existing exit code conventions where possible.

Connectivity should have predictable semantics.

Recommended:

```text
0   successful connectivity / reachable
1   expected negative result such as refused or timeout
2   invalid CLI input
3   unexpected/system error
```

The exact mapping should be reconciled with the existing v0.1-v0.4 implementation before coding.

The important rule is:

> A normal network result must not be confused with an invalid command or an internal program failure.

For example:

```text
REFUSED
```

is not necessarily an application error.

---

# 41. Error Output

Errors intended for humans should go to stderr.

Normal structured results should go to stdout.

For example:

```text
stdout:
ADDRESS              STATUS
localhost:8080       REFUSED
```

Unexpected CLI/configuration error:

```text
stderr:
invalid endpoint: localhost
```

Do not mix diagnostic logs into JSON stdout.

---

# 42. Performance

The normal command:

```bash
portcheck 8080
```

must remain lightweight.

Do not introduce connectivity work into normal port checks.

Connectivity only happens when requested.

Doctor may perform multiple operations because that is its explicit purpose.

Do not introduce concurrency merely because multiple checks exist.

Sequential execution is acceptable unless measurement demonstrates a real need.

---

# 43. Security and Safety

Portcheck v0.5 performs user-directed TCP connection attempts.

Keep the scope narrow.

The implementation should:

- connect only to addresses explicitly provided by the user
- perform one connection attempt
- avoid scanning
- avoid retries
- avoid background network activity
- avoid sending application payloads
- close successful connections immediately
- respect timeouts
- respect cancellation

Do not add automatic host discovery or port enumeration.

# 51. Human Review Checklist

After the agent finishes, manually inspect:

### Connectivity

- Is `--connect` actually using TCP?
- Is `DialContext` used?
- Are connections closed?
- Is timeout enforced?
- Is cancellation respected?
- Are errors classified without fragile string matching?
- Are IPv6 addresses handled correctly?

### Architecture

- Is connectivity separate from local availability?
- Is doctor composition rather than duplicated logic?
- Has `main.go` become a giant switch statement?
- Were unnecessary abstractions introduced?

### Process integration

- Does process inspection remain optional?
- Can process inspection fail without changing port status?
- Are process races handled safely?

### JSON

- Is the schema predictable?
- Are optional fields handled consistently?
- Does JSON remain machine-readable?
- Are logs/errors kept out of stdout?

### Tests

- Are tests deterministic?
- Do they avoid public internet dependencies?
- Are timeout tests portable?
- Are IPv6 tests environment-aware?
- Are existing tests still passing?

### Scope

Look specifically for accidental v0.6/v1.0 creep.

Reject implementation that adds:

```text
UDP
scanning
packet capture
HTTP probing
TLS analysis
firewall detection
service management
automatic retries
```

just because an agent decided it would be “nice to have.”

# 52. Expected v0.5 Result

After v0.5, Portcheck should be capable of answering four increasingly useful questions:

```text
v0.1
Can this local port be bound?

v0.4
What local process is using this port?

v0.5
Can I establish a TCP connection to this endpoint?

v0.5 doctor
What factual information can Portcheck gather about this local endpoint?
```

The important architectural property is that these questions remain separate.

The project should still feel like a small Go utility, not an accidental recreation of half the Linux networking stack.

---

# 53. Boundary to v1.0

v0.5 should stop here.

Later releases can improve:

- release engineering
- API stability
- cross-platform completeness
- packaging
- installation
- compatibility guarantees
- documentation
- performance measurement
- polish

Those belong to the later roadmap.

The purpose of v0.5 is to make Portcheck **diagnostically useful without making it architecturally bloated**.
