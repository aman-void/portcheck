# Portcheck v0.1

> Foundation release: a small, reliable CLI that validates ports and checks local TCP port availability.

---

## 1. Version Objective

Version `0.1.0` establishes the first usable version of Portcheck.

The release must provide a working command-line application capable of:

- accepting one or more TCP ports
- validating port numbers
- checking whether ports are available on `127.0.0.1`
- reporting `FREE` or `IN USE`
- displaying help
- displaying the version
- supporting quiet mode
- returning predictable exit codes
- handling duplicate ports
- preserving input order
- reporting errors clearly
- being tested thoroughly

The implementation must remain small and dependency-free.

- determining the final exit code

# 7. Port Validation

Accept:

```text
1
80
443
3000
8080
65535
```

Reject:

```text
0
-1
65536
99999
abc
8080abc
1.5
""
```

Ports must be decimal integers.

The accepted range is:

```text
1 <= port <= 65535
```

Whitespace behavior should be deliberate.

Prefer rejecting malformed input rather than silently transforming it.

For example:

```text
"8080abc"
```

must not become:

```text
8080
```

# 11. TCP Availability Checking

The initial implementation checks:

```text
127.0.0.1:<port>
```

For example:

```text
127.0.0.1:8080
```

The core operation should attempt to create a TCP listener.

Conceptually:

```go
listener, err := net.Listen("tcp", address)
```

If listening succeeds:

```text
FREE
```

The listener must immediately be closed.

If the address cannot be bound because another process is already using it:

```text
IN USE
```

Other errors must not automatically be classified as `IN USE`.

---

# 12. Listener Cleanup

Every successfully created listener must be closed.

The implementation should use a structure equivalent to:

```go
listener, err := net.Listen("tcp", address)
if err != nil {
    // handle error
}

defer listener.Close()
```

The exact implementation may differ.

Resource cleanup is mandatory.

Tests should detect obvious resource-management mistakes where practical.

# 13. Result Model

The checker should return structured information instead of directly printing output.

A possible model:

```go
type Status int

const (
    StatusFree Status = iota
    StatusInUse
    StatusError
)
```

and:

```go
type Result struct {
    Port   int
    Status Status
    Err    error
}
```

The exact representation is an implementation detail.

The important requirement is:

```text
Detection != Presentation
```

# 14. Multiple Ports

Support:

```bash
portcheck 3000 3001 3002 8080
```

Example:

```text
PORT    STATUS
3000    FREE
3001    FREE
3002    IN USE
8080    FREE
```

Every requested port should be checked independently.

One failure must not prevent other valid ports from being checked unless the failure makes further checking impossible.

---

# 15. Deterministic Output

Input order must be preserved.

Input:

```bash
portcheck 8080 3000 5432
```

Output:

```text
PORT    STATUS
8080    IN USE
3000    FREE
5432    FREE
```

Do not reorder ports numerically.

Do not output based on completion order.

Sequential checking is acceptable and preferred for v0.1.

---

# 16. Duplicate Ports

Duplicate ports should be treated as a single check.

Input:

```bash
portcheck 8080 8080 3000
```

Expected conceptual output:

```text
PORT    STATUS
8080    IN USE
3000    FREE
```

The first occurrence determines output ordering.

For example:

```bash
portcheck 3000 8080 3000
```

should produce:

```text
3000    FREE
8080    IN USE
```

not:

```text
8080
3000
```

and not duplicate `3000`.

# 19. Exit Codes

Implement:

```text
0 = all requested ports are free
1 = one or more requested ports are in use
2 = invalid CLI input
3 = unexpected/system error
```

Examples:

```bash
portcheck 3000
echo $?
```

If free:

```text
0
```

If in use:

```text
1
```

Invalid:

```bash
portcheck 70000
```

should result in:

```text
2
```

Unexpected system errors should result in:

```text
3
```

The exact OS-specific circumstances that produce code `3` may be limited in v0.1.

---

# 20. Error Output

Normal errors must go to stderr.

Invalid input example:

```text
error: invalid port "70000": must be between 1 and 65535
```

Another:

```text
error: invalid port "abc": must be a number
```

Do not print vague messages such as:

```text
something went wrong
```

Do not panic for invalid user input.

---

# 21. Standard Output vs Standard Error

Use:

```text
stdout
```

for successful command results.

Use:

```text
stderr
```

for:

- invalid input
- system errors
- diagnostic messages

This distinction is important for scripting.

For example:

```bash
portcheck 8080 > result.txt
```

should not unexpectedly put error diagnostics into `result.txt`.

## 24.2 Checker tests

Use an actual listener.

Example:

```go
listener, err := net.Listen("tcp", "127.0.0.1:0")
```

Get the dynamically allocated port:

```go
addr := listener.Addr().(*net.TCPAddr)
port := addr.Port
```

While the listener is open:

```text
Check(port) → IN USE
```

Close the listener:

```go
listener.Close()
```

Then:

```text
Check(port) → FREE
```

Do not hardcode a supposedly unused port.
